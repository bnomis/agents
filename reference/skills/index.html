    Skills¶

    Each skill is a directory under claude/skills/<name>/ holding a SKILL.md and any scripts or templates it uses. bin/install-claude.sh links claude/ into ~/.claude/, so every skill is available in every project as ~/.claude/skills/<name>/.

    Invoke a skill in Claude Code as /<name> [args], or by asking for what it does: the when_to_use list in each skill's frontmatter names the phrases that trigger it ("ship it", "add a todo").

    The /auditme and /auditme-project-setup skills are in the auditor repository (bnomis/auditor, https://bnomis.github.io/auditor/reference/skills/).

    Common behaviour:

    • The planning and TODO skills check git status first and ask whether to commit uncommitted changes before touching a file they own.
    • They ask before committing, and do not push unless asked. The exception is /shipit, whose job is to commit, merge and push.
    • Steps that change something outside the working tree (deleting branches, for example) are confirmed with the user first.
    • Questions to the user go through Claude Code's AskUserQuestion tool where the skill names it.

    Summary¶

    Planning¶

    Skill Invocation Purpose
    specdev /specdev <spec-name> Write, review or update a spec; detect drift from the code
    taskdev /taskdev <spec-name-or-path> Turn a spec or review into an ordered task list
    testplan /testplan [scope] Find testing gaps and write a test plan

    TODO workflow¶

    Skill Invocation Purpose
    todo-add /todo-add [description] File one verified, dated finding in TODO.md, in order
    todo-review /todo-review Re-check, consolidate and reorder the whole of TODO.md
    todo-do /todo-do [item title] Do the first (or named) item, or start a spec for it
    todo-run-order /todo-run-order <items> [run order name] Turn chosen items into specs, task lists and an order file for /rro
    survey /survey [root] Survey every repository for unfinished plans, fixable failures, doable items and stale branches; file the findings
    test-log-review /test-log-review [root] [--glob PATTERN] Trace the failures and warnings in every repository's newest pytest logs; review page; file the approved fixes
    note-add /note-add [note] Append a dated, self-explanatory note to NOTES.md

    /specdev¶

    /specdev <SPEC-NAME>

    With no argument, lists specs from agents/specs/index.md and asks which. The name is slugified (lowercase ASCII alphanumerics, spaces to hyphens, repeated hyphens collapsed): "C++ Parser v2.0" becomes c-parser-v20.

    • Reads: AGENTS.md, README.md, agents/specs/index.md, the spec, and the implementation at the spec's module location.
    • New spec: interviews the user, writes a draft from the template (Version, Status: proposed, Date, then Module location, API, Error handling, Implementation, Settings, External dependencies), and adds it to the index.
    • Existing spec: runs drift detection against the code when it exists, checks the spec against the template and validation criteria, and suggests changes. Drift findings are never resolved without the user choosing a direction for each one.
    • Stops for: interview answers; each drift item (update spec, update code, or skip); commit.
    • Writes: agents/specs/<slug>/spec.md, agents/specs/index.md. Commits only the spec file, with a message such as docs(specs): add error handling to <SLUG> spec.

    One spec covers one repository and is self-contained; cross-repository work is one spec per repository.

    /taskdev¶

    /taskdev <SPEC-NAME>
/taskdev <SPEC-PATH>

    An argument containing / is a path. A path that is not agents/specs/<slug>/spec.md (an audit review or test plan, for example) is non-spec input: the slug is the parent directory's name, and tasks cite Source instead of Spec.

    • Reads: the spec and its sibling documents, agents/tasks/index.md, earlier agents/tasks/<slug>/tasks-*.md, and the code under src/ to mark work already done.
    • Writes: agents/tasks/<slug>/tasks-N.md (never overwrites; N increments) and agents/tasks/index.md.
    • Stops for: an ambiguous spec (offers /specdev first, or proceeds with caveats); tasks that need a user decision; review of the list; commit.

    Each task carries status, priority, complexity, spec reference, subtasks, acceptance criteria, notes, and a Definition of Done naming the project's own check commands literally. Per-task checks are scoped to the changed files; the last task runs the whole-tree lint and the full affected-tests run, and sets the spec's status to implemented. No task edits another repository.

    /testplan¶

    /testplan                 # every module under src/
/testplan <module-path>   # one module and its tests
/testplan <spec-name>     # a spec's implementation
    • Reads: AGENTS.md, the modules in scope and their tests (src/tests/), earlier plans in agents/test-plans/, and uv run pytest --co -q.
    • Writes: agents/test-plans/plan-N.md (never overwrites), capped at 20 recommendations, favouring branching logic, error paths and edge cases.
    • Then: if there are recommendations, runs /taskdev agents/test-plans/plan-N.md.
    • Stops for: commit (docs(tests): add plan-N).

    /todo-add¶

    /todo-add <description>
/todo-add                 # files the finding just established in the conversation
    • Reads: the project's TODO.md convention section (in AGENTS.md or CLAUDE.md), TODO.md in full, the tail of DONE.md, and the code needed to confirm the cause.
    • Writes: one item in TODO.md: a specific ## title, the dated finding (inside the project's accept markers), the cause with path:line, and a Fix direction. It is inserted in implementation order, never appended. A finding that shares a root cause with an open item joins it as a ### finding; one that touches several items is proposed as a consolidation first.
    • Stops for: uncommitted TODO.md changes; a proposed consolidation; commit (docs(todo): ...).

    A fix that belongs to another repository is filed in that repository's TODO.md. Conventions shared by the TODO skills are in claude/skills/todo-review/conventions.md; a project's own TODO.md section overrides them.

    /todo-review¶

    /todo-review
    • Reads: TODO.md, DONE.md, and the project's specs, task lists, reviews, code markers (TODO, FIXME, expected failures) and recent commit bodies, looking for promised work no item records.
    • Proposes, before any edit: items to move to DONE.md with evidence, stale premises, missing items, groups sharing a root cause, and the new order, shown as a table.
    • Writes, once confirmed: TODO.md reordered and consolidated (original bodies kept verbatim under ###), finished items appended to DONE.md with a Done: line, missing items added, stale premises corrected with a dated note.
    • Verifies: saves HEAD:TODO.md to a scratch file first, then runs python3 ~/.claude/skills/todo-review/verify_bodies.py <before> TODO.md DONE.md, which exits non-zero if any original item body is lost or altered.
    • Stops for: uncommitted TODO.md changes; the proposal; commit (docs(todo): ...).

    Order, highest first: work-losing defects, blockers, waste, features (each before what it makes cheaper or safer), then deferred items.

    /todo-do¶

    /todo-do
/todo-do <item title>

    Re-checks the item is still open, still true, and not one symptom of a shared cause (if it is, proposes /todo-review and stops). Then sizes it:

    Size Condition Action
    Small One logical change; no artefact, contract or public API change; no spec section rewrite; no paid run or real-data change Fix on a branch, test first for defects, run the project's checks, move the item to DONE.md with a Done: line, add dated notes to other items whose path:line moved
    Large Anything else, or the item says it goes through a spec Run /specdev, stop for spec review, offer /taskdev, add a Spec: ...; tasks: ... line to the item; it moves to DONE.md when the task list finishes
    • Stops for: a done or stale item; a shared cause; spec review; a paid LLM run (asks for provider and a cost estimate); commit.
    • Backs up real project artefacts before a run that rewrites them; a new defect found mid-run is filed with /todo-add, not fixed in place.

    /todo-run-order¶

    /todo-run-order <items> [run order name]

    <items> picks TODO.md items by position, counting ## headings from 1, as numbers and ranges: 1-3,5,8. Starts from the main checkout on a clean default branch level with its remote.

    • Re-checks each item as /todo-do does, sizes it, and plans a task list per small item and one or more specs per large one, each in this repository.
    • Writes the specs with /specdev, then one review of all of them, agents/reviews/order-<slug>-specs.md, with its page, naming every prerequisite the operator must provide; stops until it is answered.
    • Writes a task list per spec with /taskdev. Each list's last task saves its final test output where /rro's merge gate reads it, and each item gets its Spec: ...; tasks: ... line.
    • Writes agents/tasks/order-<slug>.md, taking the settings from the newest order file or the project's rules, and checks it with /rro's parser.
    • Stops for: a done, stale or shared-cause item; the specs' review; a required setting nothing gives; commit. It never starts the order.

    /survey¶

    /survey [root]

    Answers, for every repository at and below the root: which specs and task lists are not implemented, which expected failures and known bugs could be fixed, which TODO.md items can be done now, and which branches and worktrees are stale.

    • Runs: python3 ~/.claude/skills/survey/inventory.py <root>, which prints each repository's status, worktrees, branches (merged or not), task lists with open tasks and specs not marked implemented. Then one read-only subagent per large repository, or per group of small ones, reads TODO.md, test markers, reviews and specs.
    • Reports under the five questions, after checking in the code every finding it recommends acting on. Repository state is given with the time it was checked.
    • Files, on request: each finding in the TODO.md of the repository where its fix is made, by the todo-add conventions. A finding blocked on an upstream release, people (labelling, native readers), data or a deferred decision is filed as deferred; an item already fixed moves to DONE.md.
    • Hands over: the changed files, a table of what was filed, and an implementation order saying what can run in parallel.
    • Stops for: the request to file; commit (docs(todo): ..., one per repository). It never deletes branches (that is /cleanup) or pushes.

    /test-log-review¶

    /test-log-review [root] [--glob PATTERN]

    Reads the newest pytest log of each kind (a full run, a correctness run) in every repository at and below the root, and turns its failures and warnings into reviewed, filed work.

    • Runs: python3 ~/.claude/skills/test-log-review/scan.py <root>, which prints each log's summary line, its FAILED and ERROR lines and its warnings grouped by message, counting from pytest's own summary line. Then read-only subagents trace each warning to its source: one for third-party warnings shared across repositories, one per repository or group for the rest.
    • Reviews: a review document and an interactive page built from page-template.html and checked with check-page.js: real defects, test-side fixes and third-party warnings to approve or flag, and decisions for fixes that change output or upgrade a recorded dependency.
    • Files, after the answers: each approved fix in the TODO.md of the repository where it is made, by the todo-add conventions, with any correction a filing agent finds recorded in the review.
    • Hands over: an implementation order in waves, a shared-environment change first and alone.
    • Stops for: the review's answers; commit (docs(todo): ..., one per repository). It never runs the test suite or pushes.

    /note-add¶

    /note-add <the note>
/note-add                 # asks what to note
    • Reads: NOTES.md in the repository root (offers to create it), and the repository to fill in missing context.
    • Writes: appends one note to NOTES.md:
    ## <short title>

Added YYYY-MM-DD. <the note>

    Adds to an existing note on the same subject instead of duplicating it. Never edits other notes. - Stops for: up to a few clarifying questions on what a later reader would miss (what, why, where, when, who); a preview with add / change / cancel; commit (docs(notes): <subject>).

    Open work with a cause belongs in TODO.md; the skill redirects to /todo-add.

    /shipit¶

    /shipit [commit message hint]

    It is not called /ship: Claude Code has a built-in /ship (commit, open a pull request and watch it), and a skill of the same name is hidden behind it.

    1. Inspects git status, diffs, branch, worktrees and recent log; stops if it sees secrets, build output, large binaries or unrelated changes.
    2. Commits by logical change, staging files by name, with conventional commit messages; fixes hook failures rather than bypassing them.
    3. On a feature branch: fetches, rebases onto origin/main, and fast-forwards main (in the worktree that holds main, if another one does).
    4. Pushes main, after git pull --rebase if origin/main moved. Never force-pushes; stops on rejection.
    5. Reports the commits, the merge and the push, with repository state stated only from a fresh git fetch and git status -sb.

    Feature branches and worktrees are left in place; use /cleanup.

    /cleanup¶

    /cleanup [repo-path]

    Works on one repository (default: the current one) and all its worktrees; never changes the remote. It reads only until the plan is approved.

    • Merged means, against the local default branch or origin/<default>: ancestry, a rebase merge (git cherry shows no +), or a squash merge (a probe commit of the branch's tree shows no +).
    • Removes: prunable worktrees; clean worktrees whose branch or detached HEAD is merged; merged local branches. Skips the main worktree, the current one, locked or dirty worktrees, and worktrees holding a submodule (for which it prints the commands to run by hand).
    • Stops for: one approval of the plan - all, a named subset, or cancel. The plan lists ignored files each worktree removal will delete.
    • Never --force on worktrees. Uses git branch -D only for a branch it proved merged by the rebase or squash test.

    /paper-pdf-hunter¶

    /paper-pdf-hunter <PAPER-LIST> <OUTPUT-FOLDER>

    Drives a real browser (Claude in Chrome preferred, else Playwright MCP; stops if neither is connected) to find a PDF for each paper in a Markdown list. It does not use scholarly APIs.

    • Reads: the Markdown list in any citation shape, extracting title, authors, year, DOI, arXiv ID and URLs.
    • Searches, stopping at the first verified PDF: arXiv or DOI landing page, Google Scholar (including all versions), preprint and repository sites, general web search, then public ResearchGate or Academia.edu copies. Shadow libraries and paywall bypasses are out of scope.
    • Verifies each file: %PDF header, size, and title on the first pages via pdftotext.
    • Writes: <FirstAuthor>_<Year>_<first-five-title-words>.pdf (with _preprint or _accepted suffixes, never overwriting) and download_report.md in the output folder. Output defaults to ./papers/ beside the list.
    • Stops for: a missing list or folder, Chrome's PDF download setting, CAPTCHAs (the user solves them), and any login it would have to perform on the user's behalf.
